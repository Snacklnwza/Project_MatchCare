# MatchCare Database Audit

> สถานะ: Analysis Draft  
> วันที่ตรวจ: 3 กันยายน 2569  
> ขอบเขต: เปรียบเทียบ ER Diagram, `Mathcare.sql` และ MatchCare MVP Requirements

## 1. สรุปผล

ER Diagram และ SQL เดิมมีโครงสร้างสอดคล้องกัน และมีแนวคิดฐานข้อมูลเชิงสัมพันธ์ที่ถูกต้องหลายส่วน เช่น Primary Key, Foreign Key และตารางกลางสำหรับความสัมพันธ์แบบหลายต่อหลาย อย่างไรก็ตาม Schema เดิมยังไม่รองรับ Supabase Auth, RLS, การซ่อนข้อมูลผู้ป่วย, การแยกใบสมัครกับคำเชิญ และกฎหนึ่งประกาศรับผู้ดูแลหนึ่งคน จึงไม่ควรนำ SQL ทั้งไฟล์ไปรันทันทีโดยไม่ปรับแก้

## 3. ส่วนที่ออกแบบมาดีและควรเก็บแนวคิดไว้

- แยกข้อมูลทั่วไปของผู้ใช้ออกจากข้อมูลเฉพาะผู้ดูแล
- ผู้ว่าจ้างหนึ่งคนมีผู้ป่วยได้หลายราย
- ใช้ตารางกลาง `Caregiver_skills` รองรับผู้ดูแลหนึ่งคนมีหลายทักษะ และทักษะหนึ่งรายการอยู่กับผู้ดูแลหลายคน
- ใช้ตารางกลาง `Job_Tags` รองรับประกาศหนึ่งรายการต้องการหลายทักษะ
- แยกคำขอจับคู่ รีวิว และเอกสารผู้ดูแลออกจากตารางหลัก
- มี Primary Key และ Foreign Key สำหรับความสัมพันธ์หลัก

## 4. ช่องว่างระหว่าง Schema เดิมกับ Requirement

| รหัส | จุดที่ต้องแก้ | ปัญหาใน Schema เดิม | แนวทางสำหรับ MVP |
|---|---|---|---|
| DB-01 | เชื่อม Supabase Auth | `Users.user_id` เป็น `integer` และไม่เชื่อม `auth.users` | ใช้ `uuid` เป็น Primary Key และ Foreign Key ไปยัง `auth.users(id)` |
| DB-02 | การสร้าง ID | ทุก ID ต้องกำหนดเอง | ใช้ UUID หรือ Identity ตามชนิดข้อมูลและหน้าที่ของตาราง |
| DB-03 | ชื่อตารางและคอลัมน์ | ใช้ตัวพิมพ์ใหญ่และรูปแบบไม่สม่ำเสมอ | ใช้ lowercase `snake_case` ทั้ง Schema |
| DB-04 | บทบาท | `role` เป็นข้อความว่างได้และรับค่าอะไรก็ได้ | กำหนด `not null` และ `check` เฉพาะค่าที่อนุญาต |
| DB-05 | ข้อมูลซ้ำ | ชื่อผู้ดูแลซ้ำทั้ง `Users` และ `Caregiver_Profiles` | เก็บชื่อใน `profiles` เพียงแห่งเดียว |
| DB-06 | สถานะผู้ดูแล | `status` และ `is_verified` แยกความหมายไม่ชัด | แยก `availability_status` กับ `verification_status` |
| DB-07 | ความเป็นส่วนตัวผู้ป่วย | `location` เก็บที่อยู่รวมในช่องเดียว | แยกจังหวัด อำเภอ ตำบล และรายละเอียดที่อยู่ |
| DB-08 | อาการและการเคลื่อนไหว | มี `Mobility_Status` ข้อความเดียวและไม่มีรายการอาการหลายค่า | แยกสถานะการเคลื่อนไหว และใช้ตารางกลางสำหรับอาการหลายรายการ |
| DB-09 | ประกาศงาน | มีเพียงเจ้าของ ผู้ป่วย สถานะ และวันที่สร้าง | เพิ่มรายละเอียดงาน เวลา พื้นที่ และข้อมูลที่จำเป็นต่อ Job Card |
| DB-10 | ประเภทคำขอ | `Match_Requests` แยกใบสมัครกับคำเชิญไม่ได้ | เพิ่ม `request_type` เป็น `application` หรือ `invitation` |
| DB-11 | คำขอซ้ำ | ผู้ดูแลคนเดิมสร้างคำขอซ้ำกับงานเดิมได้ | เพิ่ม `unique(job_id, caregiver_id)` |
| DB-12 | หนึ่งงานหนึ่งคน | ไม่มี Constraint ป้องกัน Accepted หลายรายการ | เพิ่มกฎฐานข้อมูลให้หนึ่ง `job_id` มีคำขอ Accepted ได้หนึ่งรายการ |
| DB-13 | สถานะ | Status ทุกตารางเป็นข้อความอิสระ | กำหนด `check` และ Default ตาม State Flow |
| DB-14 | รีวิวสองทาง | ไม่มี Constraint จำกัดหนึ่งรีวิวต่อฝ่ายต่องาน | เพิ่ม `unique(match_id, reviewer_id)` และ `check` คะแนน 1-5 |
| DB-15 | การตรวจเอกสาร | เก็บเพียงชนิดไฟล์ URL และวันที่อัปโหลด | เพิ่มสถานะ ผู้ตรวจ เวลาตรวจ และเหตุผลปฏิเสธ |
| DB-16 | วันและเวลา | หลายคอลัมน์ใช้ `date` จึงไม่เก็บเวลาและ Time Zone | ใช้ `timestamptz` และ Default `now()` สำหรับเหตุการณ์ระบบ |
| DB-17 | การลบข้อมูล | Foreign Key ยังไม่กำหนดผลเมื่อข้อมูลแม่ถูกลบ | กำหนด `on delete` ให้เหมาะกับประวัติและข้อมูลลูก |
| DB-18 | ความปลอดภัย | ไม่มีการเปิด RLS หรือ Policy | เปิด RLS ทุกตารางใน `public` และเขียน Policy ตามเจ้าของข้อมูล/บทบาท |

## 6. ตารางแรกสำหรับ Milestone วันอาทิตย์

เลือก `skills` เป็นตารางแรกสำหรับทดลองเชื่อม Frontend เพราะ

- เป็น Master Data ที่จะใช้จริงใน MatchCare
- ไม่มีชื่อผู้ป่วย ที่อยู่ เอกสาร หรือข้อมูลอ่อนไหว
- โครงสร้างเล็ก อธิบาย Primary Key, Unique และ Timestamp ได้ง่าย
- React สามารถอ่านรายการไปแสดงเป็น Checklist หรือ Tag ได้ทันที
- ใช้พิสูจน์เส้นทาง React -> Supabase Client -> Data API -> PostgreSQL ได้ก่อนเริ่มตารางที่มี RLS ซับซ้อน

Milestone แรกไม่ถือว่า Schema ทั้งระบบเสร็จ แต่เป็นการพิสูจน์ว่าเครื่องมือและการเชื่อมต่อทำงานก่อนขยายไปยัง `profiles` และ Auth

## 7. สิ่งที่ยังไม่ควรทำ

- ไม่รัน `Mathcare.sql` ทั้งไฟล์บน Supabase
- ไม่สร้าง Policy แบบอนุญาตทุกคนทุกการกระทำเพื่อให้ระบบรันผ่าน
- ไม่ใส่ Service Role Key ใน React หรือ `.env` ของ Frontend
- ไม่ใช้ข้อมูลผู้ป่วยหรือเอกสารจริงในการทดสอบ
- ไม่แก้ ER Diagram ก่อนที่ Logical Schema จะได้รับการตรวจและเข้าใจร่วมกัน

## 8. ลำดับการแก้ Schema

1. ยืนยันรายการตาราง Logical Schema
2. กำหนด Primary Key และ Foreign Key
3. กำหนด Cardinality และ Optionality
4. กำหนดคอลัมน์ ชนิดข้อมูล Default และ Constraint
5. กำหนด State และ Business Rule ที่ฐานข้อมูลต้องบังคับ
6. วางแผน RLS ตามตารางและบทบาท
7. เขียน SQL เป็นส่วนเล็กและทดสอบทีละส่วน
8. ปรับ ER Diagram ให้ตรงกับ SQL ที่ผ่านการทดสอบ
