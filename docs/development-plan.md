# MatchCare Development Plan

> เป้าหมาย: ระบบ MVP พร้อมสาธิตภายในวันที่ 19 กันยายน 2569  
> วันส่งเป้าหมาย: ก่อนวันที่ 20 กันยายน 2569  
> สมมติฐาน: ผู้พัฒนาหลัก 1 คน ทำงานเฉลี่ยวันละ 3-4 ชั่วโมง

## 1. หลักการของแผน

- ทำฟังก์ชัน P0 ให้ครบก่อนเริ่มงาน P1
- หยุดเพิ่มฟีเจอร์ใหม่หลังวันที่ 17 กันยายน
- วันที่ 18 ใช้ทดสอบทั้งระบบและแก้ข้อผิดพลาด
- วันที่ 19 ใช้เตรียมข้อมูลสาธิต README และหลักฐานส่งงาน
- วันที่ 20 เป็นวันสำรอง ไม่ใช่วันพัฒนาฟีเจอร์หลัก
- ใช้ข้อมูลสมมติเท่านั้น ห้ามใช้ข้อมูลผู้ป่วยหรือเอกสารจริง

## 2. ขอบเขตที่ต้องเสร็จ

### P0 - ต้องมี

- สมัคร เข้าสู่ระบบ และแยกบทบาทผู้ว่าจ้าง ผู้ดูแล และ Admin
- ผู้ว่าจ้างจัดการผู้ป่วยและประกาศงาน
- ผู้ดูแลจัดการโปรไฟล์ ทักษะ ความพร้อม และเอกสารยืนยัน
- Admin อนุมัติหรือปฏิเสธผู้ดูแล
- ผู้ดูแลดูประกาศได้ แต่สมัครได้เมื่อ Verified เท่านั้น
- ผู้ว่าจ้างค้นหาผู้ดูแลและส่งคำเชิญได้หลายคน
- หนึ่งประกาศตอบรับผู้ดูแลได้หนึ่งคน
- ซ่อนชื่อผู้ป่วย ที่อยู่ละเอียด และข้อมูลติดต่อก่อนจับคู่สำเร็จ
- เชื่อม React กับ Supabase และแสดง CRUD ได้จริง
- เปิด RLS และทดสอบสิทธิ์ทั้งกรณีที่อนุญาตและปฏิเสธ
- มี Git history, README, Trello และหลักฐานการทำงาน

### P1 - ทำเมื่อ P0 ผ่านแล้ว

- ประวัติงานและการยกเลิกงาน
- รีวิวสองทาง
- การจัดลำดับผู้ดูแลตามจำนวนทักษะที่ตรงกัน
- Responsive Design สำหรับหน้าหลัก

## 4. Definition of Done รายวัน

งานหนึ่งรายการจะย้ายไป Done ได้เมื่อครบทุกข้อที่เกี่ยวข้อง

- ฟังก์ชันทำงานตาม Acceptance Criteria
- ทดสอบ Happy Path อย่างน้อยหนึ่งกรณี
- ทดสอบกรณีข้อมูลผิดหรือไม่มีสิทธิ์อย่างน้อยหนึ่งกรณี
- ไม่มี error ค้างใน Browser Console หรือ SQL Editor
- ไม่มี Secret หรือข้อมูลจริงในไฟล์
- รัน `git status` และตรวจไฟล์ก่อน commit
- Commit message อธิบายงานย่อยได้ชัดเจน
- Push branch ขึ้น GitHub แล้ว
- อัปเดตการ์ด Trello พร้อมหลักฐานหรือข้อความสรุป

## 5. รูปแบบ Trello Board

ใช้สถานะอย่างน้อยดังนี้

```text
Backlog -> To Do -> In Progress -> Testing/Review -> Done
                         \-> Blocked
```

กติกาใช้งาน

- ใน `In Progress` มีงานพร้อมกันไม่เกิน 1-2 การ์ดต่อคน
- หนึ่งการ์ดควรเสร็จภายในครึ่งวันถึงหนึ่งวัน
- ชื่อการ์ดขึ้นต้นด้วยรหัส เช่น `DB-01`, `FE-03`, `TEST-02`
- ใส่ Acceptance Criteria สั้น ๆ ในทุกการ์ด
- ถ้าติดเกิน 60 นาที ให้ย้ายไป Blocked และเขียนสาเหตุ
- ห้ามย้ายไป Done เพียงเพราะเขียนโค้ดเสร็จ ต้องทดสอบก่อน

## 6. ตัวอย่างการแบ่งการ์ด

### Requirement และ Database

- `REQ-01` ตอบ Open Items ที่กระทบ Schema
- `DB-01` ตรวจ Entity และ Relationship
- `DB-02` สร้าง Core Tables และ Constraints
- `DB-03` เพิ่ม Seed Data
- `SEC-01` สร้าง RLS สำหรับข้อมูลเจ้าของ
- `SEC-02` สร้าง RLS สำหรับ Verified Caregiver
- `SEC-03` ทดสอบการซ่อนข้อมูลส่วนตัว

### Frontend

- `FE-01` ตั้งค่า Supabase Client
- `FE-02` ทำหน้า Register และ Login
- `FE-03` ทำ Role-based Navigation
- `FE-04` ทำ Patient CRUD
- `FE-05` ทำ Caregiver Profile
- `FE-06` ทำ Admin Verification
- `FE-07` ทำ Job CRUD และ Job Board
- `FE-08` ทำ Application และ Invitation
- `FE-09` ทำ Accept/Reject และ Match Result

### Testing และส่งงาน

- `TEST-01` ทดสอบ Employer Flow
- `TEST-02` ทดสอบ Caregiver Flow
- `TEST-03` ทดสอบ Admin Flow
- `TEST-04` ทดสอบ RLS กรณีไม่มีสิทธิ์
- `DOC-01` ปรับ README และวิธีติดตั้ง
- `DOC-02` รวบรวมหลักฐาน CRUD และ RLS
- `DEMO-01` เตรียมบัญชีและข้อมูลสาธิต
- `DEMO-02` ซ้อมนำเสนอ End-to-End

## 7. กฎการตัดขอบเขตเมื่อช้ากว่าแผน

- ถ้าช้ากว่าแผน 1 วัน ให้ลด Animation และการตกแต่งที่ไม่กระทบการใช้งาน
- ถ้าช้ากว่าแผน 2 วัน ให้ย้าย Review, Dashboard และตัวกรองขั้นสูงไป Future Features
- ถ้าช้ากว่าแผน 3 วัน ให้เน้นหนึ่ง End-to-End Flow ที่ทำงานจริงและหลักฐาน RLS ก่อนหน้าจอรอง
- ห้ามตัด Authentication, Database Constraints, RLS, Verified Rule หรือกฎหนึ่งประกาศต่อหนึ่งผู้ดูแล

## 8. User Flow สำหรับเดโม

1. Caregiver สมัครและกรอกโปรไฟล์ แต่ยังสมัครงานไม่ได้
2. Admin ตรวจข้อมูลและเปลี่ยนสถานะ Caregiver เป็น Verified
3. Employer สมัคร เพิ่มผู้ป่วย และสร้างประกาศงาน
4. Caregiver ดูประกาศและสมัครงาน
5. Employer กดค้นหาผู้ดูแล ส่งคำเชิญ และตอบรับผู้ดูแลหนึ่งคน
6. ระบบป้องกันการตอบรับผู้ดูแลคนที่สอง
7. คู่สัญญาเห็นข้อมูลติดต่อหลังจับคู่ แต่บัญชีอื่นมองไม่เห็น
8. แสดงผลการทดสอบ CRUD และ RLS จากระบบ
