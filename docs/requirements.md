# MatchCare System Requirements

> เวอร์ชัน: 0.3 (MVP Baseline)
>
> วันที่ปรับปรุง: 3 กันยายน 2569
>
> สถานะ: ทีมยืนยันขอบเขตเบื้องต้นแล้ว รอตรวจสอบกับอาจารย์

## 1. ภาพรวมระบบ

MatchCare เป็นเว็บแอปพลิเคชันศูนย์กลางสำหรับจับคู่ระหว่างผู้ว่าจ้างหรือญาติผู้ป่วยกับผู้ดูแล ผู้ว่าจ้างสามารถสร้างข้อมูลผู้ป่วย สร้างประกาศงาน และค้นหาผู้ดูแล ส่วนผู้ดูแลสามารถสร้างโปรไฟล์ทักษะและค้นหาประกาศงานที่เหมาะสม ระบบใช้ทักษะของผู้ดูแลและความต้องการของผู้ป่วยเป็นข้อมูลประกอบการค้นหาและจัดลำดับผู้ดูแลที่ใกล้เคียง โดยมีผู้ดูแลระบบทำหน้าที่ตรวจสอบและอนุมัติบัญชีผู้ดูแลเพื่อเพิ่มความน่าเชื่อถือของแพลตฟอร์ม

ระบบนี้เป็นโครงงานรายวิชาฐานข้อมูล โดยมุ่งเน้นการออกแบบฐานข้อมูล PostgreSQL บน Supabase การทำ CRUD การกำหนดสิทธิ์ด้วย Row Level Security (RLS) และการเชื่อมต่อฐานข้อมูลกับ Frontend มากกว่าการสร้างระบบเชิงพาณิชย์ที่สมบูรณ์

## 2. ปัญหาที่ต้องการแก้ไข

1. การหาผู้ดูแลในปัจจุบันมักทำผ่านสื่อสังคมออนไลน์ ทำให้ประกาศกระจัดกระจาย มีข้อความสแปม และขาดระบบคัดกรองที่น่าเชื่อถือ
2. ข้อมูลในประกาศงานมักไม่ครบถ้วน ผู้ดูแลจึงไม่ทราบสภาพผู้ป่วยและหน้าที่ที่แท้จริงก่อนรับงาน
3. ทักษะของผู้ดูแลอาจไม่ตรงกับความต้องการของผู้ป่วย ส่งผลให้ผู้ดูแลไม่สามารถทำงานต่อและออกจากงานเร็วกว่าที่คาด
4. ผู้ว่าจ้างไม่มีพื้นที่กลางสำหรับค้นหา กรอง และเปรียบเทียบผู้ดูแลตามทักษะ ประสบการณ์ ความพร้อม และคะแนนรีวิว
5. ผู้ดูแลไม่มีพื้นที่กลางสำหรับค้นหางานที่ตรงกับทักษะของตนเอง
6. การเปิดเผยชื่อผู้ป่วย ที่อยู่ และข้อมูลติดต่อบนพื้นที่สาธารณะก่อให้เกิดความเสี่ยงด้านความเป็นส่วนตัว

## 3. เป้าหมายของระบบ

1. จัดเก็บข้อมูลผู้ป่วย ความต้องการดูแล ทักษะผู้ดูแล และประกาศงานในรูปแบบที่มีโครงสร้าง
2. ช่วยให้ผู้ว่าจ้างค้นหาและเปรียบเทียบผู้ดูแลที่มีทักษะตรงหรือใกล้เคียงกับความต้องการ
3. ช่วยให้ผู้ดูแลค้นหาประกาศงานที่เหมาะสมกับทักษะและความพร้อมของตนเอง
4. ลดความคลาดเคลื่อนระหว่างรายละเอียดงานกับความสามารถของผู้ดูแล
5. เพิ่มความน่าเชื่อถือด้วยกระบวนการตรวจสอบและอนุมัติผู้ดูแลโดย Admin
6. จำกัดการเปิดเผยข้อมูลส่วนตัวตามสถานะการจับคู่และบทบาทของผู้ใช้งาน
7. แสดงหลักฐานการใช้งานฐานข้อมูลจริง ได้แก่ การอ่าน เพิ่ม แก้ไข และลบข้อมูล รวมถึงการควบคุมสิทธิ์ด้วย RLS

## 4. ผู้ใช้งานและสิทธิ์

### 4.1 ผู้ว่าจ้าง (Employer)

ผู้ว่าจ้างคือญาติผู้ป่วยหรือผู้ดูแลหลักที่ต้องการค้นหาผู้ดูแล โดยสามารถดำเนินการดังต่อไปนี้

- สมัครสมาชิก เข้าสู่ระบบ และจัดการโปรไฟล์ของตนเอง
- เพิ่ม ดู แก้ไข และลบข้อมูลผู้ป่วยที่ตนเองเป็นเจ้าของ
- สร้าง แก้ไข เปิดรับ และยกเลิกประกาศงานของตนเอง
- ค้นหาและกรองผู้ดูแลตามทักษะ ประสบการณ์ ความพร้อม และข้อมูลที่อนุญาตให้แสดง
- กดปุ่มค้นหาผู้ดูแลที่ตรงหรือใกล้เคียงกับความต้องการของประกาศ
- ส่งคำเชิญไปยังผู้ดูแลได้มากกว่าหนึ่งคนในระหว่างที่ยังไม่มีผู้ตอบรับงาน
- ดูรายชื่อผู้สมัครและคำเชิญของประกาศที่ตนเองเป็นเจ้าของ
- ตอบรับหรือปฏิเสธผู้ดูแล
- ดูประวัติงานและเขียนรีวิวผู้ดูแลหลังงานเสร็จสิ้น

### 4.2 ผู้ดูแล (Caregiver)

ผู้ดูแลคือบุคคลที่ต้องการหางานดูแลผู้ป่วย โดยสามารถดำเนินการดังต่อไปนี้

- สมัครสมาชิก เข้าสู่ระบบ และสร้างโปรไฟล์ผู้ดูแล
- ระบุทักษะ ประสบการณ์ ช่วงเวลาที่สะดวก และสถานะพร้อมรับงาน
- อัปโหลดเอกสารสำหรับขอรับการตรวจสอบ
- ดูและค้นหาประกาศงานได้แม้สถานะยังไม่ผ่านการตรวจสอบ
- สมัครงานได้เฉพาะเมื่อสถานะเป็น `verified`
- ดู ตอบรับ หรือปฏิเสธคำเชิญจากผู้ว่าจ้าง
- ถอนใบสมัครของตนเองได้ก่อนมีการตอบรับ
- ดูประวัติงานและเขียนรีวิวผู้ว่าจ้างหลังงานเสร็จสิ้น

### 4.3 ผู้ดูแลระบบ (Admin)

Admin ทำหน้าที่สร้างความน่าเชื่อถือและควบคุมคุณภาพข้อมูล โดยสามารถดำเนินการดังต่อไปนี้

- ดูรายชื่อผู้ดูแลที่รอการตรวจสอบ
- ดูข้อมูลและเอกสารที่ผู้ดูแลส่งมาเพื่อประกอบการตรวจสอบ
- อนุมัติหรือปฏิเสธการยืนยันผู้ดูแล พร้อมบันทึกสถานะและเวลาที่ตรวจสอบ
- ดูข้อมูลที่จำเป็นต่อการตรวจสอบและแก้ไขปัญหาของระบบตามสิทธิ์ที่กำหนด

## 5. ขอบเขต MVP

### 5.1 ระบบสมาชิกและบทบาท

- `FR-01` ผู้ใช้สามารถสมัครสมาชิกและเข้าสู่ระบบด้วย Supabase Auth
- `FR-02` ผู้ใช้หนึ่งบัญชีเลือกบทบาทหลักได้หนึ่งบทบาท ได้แก่ `employer`, `caregiver` หรือ `admin`
- `FR-03` ระบบนำผู้ใช้ไปยังหน้าที่เหมาะสมตามบทบาทหลังเข้าสู่ระบบ
- `FR-04` ผู้ใช้สามารถดูและแก้ไขข้อมูลโปรไฟล์ของตนเอง
- `FR-04A` โปรไฟล์เก็บหมายเลขโทรศัพท์เป็นข้อมูลติดต่อหลัก และเก็บ Line ID เป็นข้อมูลเสริมที่ไม่บังคับกรอก

### 5.2 ข้อมูลผู้ป่วย

- `FR-05` ผู้ว่าจ้างสามารถเพิ่ม ดู แก้ไข และลบข้อมูลผู้ป่วยของตนเอง
- `FR-06` ผู้ป่วยหนึ่งรายสามารถมีอาการหรือเงื่อนไขการดูแลได้หลายรายการ
- `FR-07` ผู้ป่วยหนึ่งรายสามารถมีทักษะผู้ดูแลที่ต้องการได้หลายรายการ
- `FR-08` ระบบต้องตรวจสอบข้อมูลสำคัญก่อนบันทึก เช่น ระดับการช่วยเหลือตนเองและทักษะที่ต้องการอย่างน้อยหนึ่งรายการ

### 5.3 โปรไฟล์และการยืนยันผู้ดูแล

- `FR-09` ผู้ดูแลสามารถสร้างและแก้ไขโปรไฟล์ ทักษะ ประสบการณ์ และสถานะพร้อมรับงาน
- `FR-10` ผู้ดูแลหนึ่งคนสามารถมีทักษะได้หลายรายการ
- `FR-11` ผู้ดูแลสามารถส่งเอกสารเพื่อขอรับการตรวจสอบ
- `FR-11A` การขอรับการตรวจสอบต้องมีเอกสารระบุตัวตนแบบข้อมูลสมมติอย่างน้อยหนึ่งรายการ
- `FR-11B` ใบรับรองการดูแลหรือเอกสารคุณวุฒิเป็นข้อมูลเสริมและไม่บังคับสำหรับ MVP
- `FR-12` Admin สามารถเปลี่ยนสถานะการตรวจสอบเป็น `pending`, `verified` หรือ `rejected`
- `FR-13` ระบบแสดงเครื่องหมาย Verified เฉพาะผู้ดูแลที่ได้รับอนุมัติแล้ว

### 5.4 ประกาศงาน

- `FR-14` ผู้ว่าจ้างสามารถสร้างประกาศจากข้อมูลผู้ป่วยที่ตนเองเป็นเจ้าของ
- `FR-15` ประกาศต้องระบุรายละเอียดงาน จังหวัด อำเภอ ช่วงเวลาทำงาน และทักษะที่ต้องการ
- `FR-16` ผู้ว่าจ้างสามารถแก้ไข ยกเลิก และดูสถานะประกาศของตนเอง
- `FR-17` ผู้ดูแลสามารถดู ค้นหา และกรองประกาศที่เปิดรับได้
- `FR-18` การ์ดประกาศสาธารณะต้องไม่แสดงชื่อผู้ป่วย ที่อยู่โดยละเอียด หรือข้อมูลติดต่อ

### 5.5 การค้นหาและจับคู่

- `FR-19` ผู้ว่าจ้างเป็นผู้กดปุ่มเริ่มค้นหาผู้ดูแลสำหรับประกาศแต่ละรายการ
- `FR-20` ระบบแสดงผู้ดูแลที่มีสถานะ `verified` และพร้อมรับงาน โดยเรียงตามจำนวนหรือสัดส่วนทักษะที่ตรงกับประกาศ
- `FR-21` ผู้ว่าจ้างสามารถส่งคำเชิญไปยังผู้ดูแลหลายคนได้ ตราบใดที่ประกาศยังไม่มีผู้ดูแลที่ได้รับการตอบรับ
- `FR-22` ผู้ดูแลที่มีสถานะ `verified` สามารถสมัครประกาศที่เปิดรับได้
- `FR-23` ผู้ว่าจ้างสามารถตอบรับหรือปฏิเสธใบสมัคร
- `FR-24` ผู้ดูแลสามารถตอบรับหรือปฏิเสธคำเชิญ
- `FR-25` หนึ่งประกาศมีผู้ดูแลที่ได้รับการยืนยันให้ทำงานได้เพียงหนึ่งคน
- `FR-26` เมื่อการจับคู่หนึ่งรายการสำเร็จ คำขออื่นที่ยังรออยู่ของประกาศเดียวกันต้องไม่สามารถถูกตอบรับซ้ำได้

### 5.6 ประวัติงานและรีวิว

- `FR-27` ผู้ว่าจ้างและผู้ดูแลสามารถดูรายการงานปัจจุบันและประวัติงานของตนเอง
- `FR-28` ผู้ว่าจ้างสามารถเปลี่ยนงานจาก `matched` เป็น `in_progress` และจาก `in_progress` เป็น `completed`
- `FR-29` ผู้ว่าจ้างและผู้ดูแลสามารถให้คะแนน 1-5 ดาวและเขียนรีวิวซึ่งกันและกันหลังงานเสร็จสิ้น
- `FR-30` ผู้ใช้แต่ละฝ่ายรีวิวคู่สัญญาได้หนึ่งครั้งต่อหนึ่งงาน
- `FR-31` ก่อนจับคู่ ผู้ว่าจ้างสามารถยกเลิกประกาศของตนเองได้
- `FR-32` หลังจับคู่ ผู้ว่าจ้างหรือผู้ดูแลที่เป็นคู่สัญญาสามารถยกเลิกงานได้โดยต้องระบุเหตุผล

## 6. กฎทางธุรกิจ

- `BR-01` ผู้ใช้หนึ่งบัญชีมีบทบาทหลักได้เพียงหนึ่งบทบาท
- `BR-02` ผู้ดูแลที่ยังไม่ผ่านการตรวจสอบสามารถดูประกาศได้ แต่ไม่สามารถสมัครงานได้
- `BR-03` ระบบค้นหาและคำเชิญควรแสดงเฉพาะผู้ดูแลที่ผ่านการตรวจสอบและมีสถานะพร้อมรับงาน
- `BR-04` การค้นหาผู้ดูแลเริ่มเมื่อผู้ว่าจ้างกดปุ่มค้นหา ไม่ทำงานอัตโนมัติทันทีที่สร้างประกาศ
- `BR-05` ความเหมาะสมเบื้องต้นคำนวณจากจำนวนทักษะที่ผู้ดูแลมีตรงกับทักษะที่ประกาศต้องการ โดยผู้ว่าจ้างเป็นผู้ตัดสินใจขั้นสุดท้าย
- `BR-06` ผู้ว่าจ้างส่งคำเชิญสำหรับประกาศเดียวกันได้มากกว่าหนึ่งคน
- `BR-07` หนึ่งประกาศมีผู้ดูแลที่ได้รับการตอบรับเพื่อทำงานได้เพียงหนึ่งคน
- `BR-08` เมื่อมีผู้ดูแลได้รับการตอบรับแล้ว คำเชิญหรือใบสมัครอื่นที่ยังรออยู่ต้องเปลี่ยนเป็นสถานะที่ไม่สามารถตอบรับได้ เช่น `not_selected`
- `BR-09` ชื่อผู้ป่วย ที่อยู่โดยละเอียด และข้อมูลติดต่อไม่แสดงต่อสาธารณะ
- `BR-10` ก่อนจับคู่ หน้าประกาศแสดงพื้นที่เพียงจังหวัดและอำเภอ หลังการจับคู่มีสถานะ `accepted` จึงเปิดเผยตำบล รายละเอียดที่อยู่ หมายเลขโทรศัพท์ และ Line ID ที่มีอยู่แก่คู่สัญญา
- `BR-11` ผู้ดูแลสามารถเปลี่ยนสถานะเป็นไม่พร้อมรับงานชั่วคราว และระบบต้องไม่นำผู้ดูแลดังกล่าวมาแสดงในผลการค้นหาหรือรับคำเชิญใหม่
- `BR-12` การรีวิวทำได้เฉพาะงานที่มีสถานะ `completed`
- `BR-13` ผู้ใช้ไม่สามารถรีวิวตนเองหรือรีวิวงานที่ตนเองไม่ได้เป็นคู่สัญญา
- `BR-14` การลบข้อมูลที่มีประวัติการทำงานแล้วควรใช้การเปลี่ยนสถานะหรือ Soft Delete แทนการลบประวัติถาวร
- `BR-15` การตอบรับใบสมัครโดยผู้ว่าจ้าง หรือการตอบรับคำเชิญโดยผู้ดูแล ถือเป็นการยินยอมของทั้งสองฝ่ายและทำให้การจับคู่สำเร็จ
- `BR-16` ผู้ว่าจ้างเป็นผู้เปลี่ยนสถานะงานจาก `matched` เป็น `in_progress` และจาก `in_progress` เป็น `completed` ใน MVP
- `BR-17` ก่อนจับคู่ ผู้ว่าจ้างเป็นผู้ยกเลิกประกาศได้ หลังจับคู่ ผู้ว่าจ้างหรือผู้ดูแลที่เป็นคู่สัญญายกเลิกงานได้และต้องระบุเหตุผล
- `BR-18` งานที่มีสถานะ `cancelled` ไม่สามารถสร้างรีวิวได้
- `BR-19` การพัฒนา ทดสอบ และสาธิตใช้เอกสารยืนยันตัวตนแบบข้อมูลสมมติเท่านั้น
- `BR-20` รายการทักษะ อาการ และสถานะการเคลื่อนไหวใน MVP เป็นข้อมูลตัวอย่างสำหรับทดสอบระบบ ไม่ใช่มาตรฐานทางการแพทย์

## 7. สถานะข้อมูลหลัก

### 7.1 สถานะการตรวจสอบผู้ดูแล

```text
pending -> verified
pending -> rejected
rejected -> pending (เมื่อส่งเอกสารใหม่)
```

### 7.2 สถานะประกาศงาน

```text
draft -> open -> matched -> in_progress -> completed
draft/open/matched/in_progress -> cancelled (ตามสิทธิ์ของแต่ละบทบาท)
```

- ผู้ว่าจ้างเป็นผู้เปิดประกาศ เริ่มงาน และจบงาน
- ก่อนจับคู่ ผู้ว่าจ้างยกเลิกประกาศได้
- หลังจับคู่ ผู้ว่าจ้างหรือผู้ดูแลที่เป็นคู่สัญญายกเลิกงานได้ โดยต้องบันทึกเหตุผล

### 7.3 ประเภทคำขอจับคู่

- `application` หมายถึงผู้ดูแลสมัครประกาศ
- `invitation` หมายถึงผู้ว่าจ้างส่งคำเชิญให้ผู้ดูแล

### 7.4 สถานะคำขอจับคู่

```text
pending -> accepted
pending -> rejected
pending -> withdrawn
pending -> not_selected
```

รายละเอียดการเปลี่ยนสถานะต้องตรวจสอบอีกครั้งร่วมกับโครงสร้างฐานข้อมูลก่อนนำไปสร้าง Constraint หรือ Policy

## 8. ความต้องการด้านข้อมูล

ระบบต้องรองรับกลุ่มข้อมูลต่อไปนี้ โดยชื่อในรายการนี้เป็นแนวคิดทางธุรกิจและยังไม่ใช่ชื่อตารางฉบับสุดท้าย

| กลุ่มข้อมูล | ตัวอย่างข้อมูล | จุดประสงค์ |
|---|---|---|
| บัญชีและโปรไฟล์ | User ID, บทบาท, ชื่อ, ช่องทางติดต่อ | ระบุตัวตนและกำหนดสิทธิ์ |
| ผู้ป่วย | ข้อมูลพื้นฐาน ระดับการช่วยเหลือตนเอง ข้อมูลสุขภาพที่จำเป็น | สร้างเคสและประกาศงาน |
| อาการหรือเงื่อนไข | ประเภทอาการและความต้องการดูแล | ใช้อธิบายเคสอย่างเป็นโครงสร้าง |
| ทักษะผู้ดูแล | ชื่อทักษะและคำอธิบาย | เชื่อมความต้องการกับความสามารถ |
| โปรไฟล์ผู้ดูแล | ประสบการณ์ ความพร้อม สถานะการตรวจสอบ | ใช้ค้นหาและเปรียบเทียบผู้ดูแล |
| เอกสารยืนยัน | ประเภทไฟล์ ตำแหน่งไฟล์ สถานะตรวจสอบ | ใช้ประกอบการอนุมัติโดย Admin |
| ประกาศงาน | ผู้ป่วย เจ้าของประกาศ เวลา พื้นที่ สถานะ | แสดงงานที่เปิดรับ |
| คำขอจับคู่ | ประเภท ผู้ส่ง ผู้รับ สถานะ เวลา | รองรับทั้งการสมัครและการเชิญ |
| งานที่จับคู่แล้ว | ประกาศ ผู้ว่าจ้าง ผู้ดูแล สถานะ | ควบคุมหนึ่งประกาศต่อหนึ่งผู้ดูแล |
| รีวิว | ผู้เขียน ผู้รับ คะแนน ข้อความ งานอ้างอิง | สร้างความน่าเชื่อถือหลังจบงาน |

### 8.1 ข้อมูลตั้งต้นสำหรับ MVP

ข้อมูลตั้งต้นต่อไปนี้นำมาจาก SQL เดิมและใช้สำหรับทดสอบการเชื่อมต่อ การกรอง และการจับคู่เท่านั้น

**ทักษะผู้ดูแล**

- Bedridden Care
- Suction
- Physical Therapy
- Feeding Tube
- First Aid

**สถานะการเคลื่อนไหวของผู้ป่วย**

- Bedridden
- Wheelchair
- Walker
- Cane

รายการเหล่านี้ไม่ถือเป็นมาตรฐานทางการแพทย์ และสามารถปรับปรุงภายหลังเมื่อได้รับคำแนะนำจากผู้เชี่ยวชาญหรืออาจารย์

## 9. ความเป็นส่วนตัวและความปลอดภัย

### 9.1 หลักการทั่วไป

- ใช้ข้อมูลสมมติในการพัฒนา ทดสอบ และนำเสนอเท่านั้น

- ไม่ใส่ Password, Secret Key, Service Role Key หรือข้อมูลสำคัญลง Git Repository
- เก็บค่าการเชื่อมต่อ Frontend ในไฟล์ `.env` และเก็บตัวอย่างชื่อค่าที่ต้องใช้ใน `.env.example`
- เปิดใช้งาน RLS สำหรับตารางที่มีข้อมูลผู้ใช้งาน
- Supabase Storage ที่เก็บเอกสารยืนยันต้องไม่เปิดเป็น Public Bucket
- แยกจังหวัด อำเภอ ตำบล และรายละเอียดที่อยู่ออกจากกัน เพื่อควบคุมการเปิดเผยและรองรับการค้นหา
- MVP ใช้จังหวัดและอำเภอเป็นตัวกรองพื้นที่ โดยไม่ใช้ GPS หรือการคำนวณระยะทาง

## 12. เกณฑ์การยอมรับระบบ

### AC-01 การสมัครและบทบาท

- ผู้ใช้สมัครและเข้าสู่ระบบได้
- ระบบบันทึกบทบาทของผู้ใช้และแสดงหน้าที่เหมาะสมกับบทบาท
- ผู้ใช้ทั่วไปไม่สามารถเรียกใช้การทำงานของ Admin ได้

### AC-02 การจัดการผู้ป่วย

- ผู้ว่าจ้างเพิ่ม ดู แก้ไข และลบหรือปิดใช้งานข้อมูลผู้ป่วยของตนเองได้
- ผู้ว่าจ้างไม่สามารถดูหรือแก้ไขผู้ป่วยของผู้ว่าจ้างคนอื่นผ่าน Frontend หรือ Supabase Client ได้
- ระบบไม่ยอมบันทึกเมื่อไม่ระบุข้อมูลสำคัญหรือทักษะที่ต้องการอย่างน้อยหนึ่งรายการ

### AC-03 การสร้างประกาศ

- ผู้ว่าจ้างสร้างประกาศจากผู้ป่วยของตนเองได้
- ประกาศที่เปิดรับปรากฏบน Job Board
- การ์ดประกาศไม่แสดงชื่อผู้ป่วย ที่อยู่โดยละเอียด หรือข้อมูลติดต่อ

### AC-04 การตรวจสอบผู้ดูแล

- ผู้ดูแลส่งข้อมูลหรือเอกสารสำหรับตรวจสอบได้
- Admin เห็นรายการที่รอตรวจและเปลี่ยนสถานะได้
- ผู้ว่าจ้างเห็นป้าย Verified หลัง Admin อนุมัติแล้วเท่านั้น

### AC-05 การสมัครงาน

- ผู้ดูแลที่ยังไม่ Verified เปิดดูประกาศได้
- ผู้ดูแลที่ยังไม่ Verified ไม่สามารถสร้างใบสมัครได้ แม้พยายามเรียกฐานข้อมูลโดยตรงผ่าน Client
- ผู้ดูแลที่ Verified สมัครประกาศที่เปิดรับได้

### AC-06 การค้นหาและคำเชิญ

- เมื่อผู้ว่าจ้างกดค้นหา ระบบแสดงผู้ดูแลที่ Verified และพร้อมรับงาน
- ผู้ดูแลที่มีทักษะตรงมากกว่าแสดงในลำดับที่เหมาะสมกว่า
- ผู้ว่าจ้างส่งคำเชิญมากกว่าหนึ่งรายการสำหรับประกาศเดียวกันได้ก่อนมีการตอบรับ

### AC-07 หนึ่งประกาศต่อหนึ่งผู้ดูแล

- เมื่อคำขอหนึ่งรายการได้รับการตอบรับ ประกาศเปลี่ยนเป็นสถานะ `matched`
- ระบบไม่อนุญาตให้คำขอรายการที่สองของประกาศเดียวกันได้รับการตอบรับ
- คำขออื่นที่ยังรออยู่เปลี่ยนเป็นสถานะที่ไม่สามารถตอบรับต่อได้

### AC-08 ความเป็นส่วนตัวหลังจับคู่

- ผู้ใช้ที่ไม่เกี่ยวข้องไม่เห็นชื่อผู้ป่วย ที่อยู่โดยละเอียด และข้อมูลติดต่อ
- คู่สัญญาเห็นข้อมูลที่จำเป็นหลังสถานะการจับคู่เป็น `accepted`
- RLS ป้องกันการอ่านข้อมูลดังกล่าวจาก Supabase Client โดยตรง

### AC-09 รีวิวสองทาง

- เมื่อสถานะงานเป็น `completed` ผู้ว่าจ้างและผู้ดูแลให้คะแนนและรีวิวกันได้
- แต่ละฝ่ายรีวิวได้ไม่เกินหนึ่งครั้งต่อหนึ่งงาน
- ผู้ใช้ที่ไม่ใช่คู่สัญญาของงานไม่สามารถสร้างรีวิวได้
- งานที่มีสถานะ `cancelled` ไม่สามารถสร้างรีวิวได้

### AC-10 หลักฐานสำหรับส่งรายวิชา

- Frontend อ่าน เพิ่ม แก้ไข และลบข้อมูลจาก Supabase ได้ตามขอบเขต
- มีตัวอย่างการทดสอบ RLS ทั้งกรณีที่อนุญาตและปฏิเสธ
- GitHub ไม่มี Secret Key หรือข้อมูลจริง
- Repository มี Commit History, README และคำแนะนำการเปิดระบบ
- Trello แสดงสถานะ To Do, In Progress และ Done ที่สอดคล้องกับงานจริง

## 14. ข้อสรุปและประเด็นที่ต้องยืนยันเพิ่มเติม

### 14.1 ข้อสรุปที่ยืนยันแล้ว

1. การตอบรับใบสมัครโดยผู้ว่าจ้าง หรือการตอบรับคำเชิญโดยผู้ดูแล ทำให้การจับคู่สำเร็จโดยไม่ต้องกดยืนยันซ้ำ
2. ผู้ว่าจ้างเป็นผู้เปลี่ยนงานจาก `matched` เป็น `in_progress` และ `completed` ใน MVP
3. ก่อนจับคู่ ผู้ว่าจ้างยกเลิกประกาศได้ หลังจับคู่ทั้งสองฝ่ายที่เป็นคู่สัญญายกเลิกได้และต้องระบุเหตุผล
4. งานที่ถูกยกเลิกไม่สามารถรีวิวได้ รีวิวสองทางทำได้เฉพาะงานที่เสร็จสมบูรณ์
5. หมายเลขโทรศัพท์เป็นข้อมูลติดต่อหลัก ส่วน Line ID เป็นข้อมูลเสริมและไม่บังคับกรอก โดยเปิดเผยหลังจับคู่สำเร็จ
6. ระบบแยกจังหวัด อำเภอ ตำบล และรายละเอียดที่อยู่ หน้าสาธารณะแสดงจังหวัดกับอำเภอ และ MVP ค้นหาตามสองระดับนี้
7. การขอ Verified ใช้เอกสารระบุตัวตนแบบข้อมูลสมมติเป็นเอกสารบังคับ ส่วนใบรับรองการดูแลเป็นเอกสารเสริม
8. ใช้รายการทักษะและสถานะการเคลื่อนไหวจาก SQL เดิมเป็น Seed Data สำหรับ MVP โดยไม่อ้างว่าเป็นมาตรฐานทางการแพทย์

### 14.2 ประเด็นที่ยังต้องยืนยัน

ไม่มี Open Item ที่ขัดขวางการออกแบบ Logical Schema ในขณะนี้ หากอาจารย์หรือทีมเปลี่ยน Requirement ต้องบันทึกการตัดสินใจใหม่ในเอกสารนี้ก่อนแก้ Schema

## 15. แหล่งที่มาของ Requirement

เอกสารนี้สรุปจากแหล่งข้อมูลต่อไปนี้ โดยเรียงลำดับความสำคัญเมื่อข้อมูลขัดแย้งกัน

1. คำชี้แจงรายวิชาและข้อสรุปจากการปรึกษาอาจารย์
2. Project Proposal ของ MatchCare
3. ข้อตกลงและการตัดสินใจล่าสุดของทีมโครงการ
4. TOR ของ Elderly Care Platform ซึ่งใช้เป็นกรอบอ้างอิง แต่ไม่ได้นำทุกโมดูลมาอยู่ใน MVP
5. ER Diagram, Database Schema, SQL, Backlog และ Figma ซึ่งต้องปรับให้สอดคล้องกับ Requirement ฉบับนี้

เมื่อ Requirement เปลี่ยน ต้องแก้เอกสารนี้ก่อนหรือพร้อมกับการแก้ ER Diagram, SQL, Backlog และหน้าจอ เพื่อให้ทุกส่วนอ้างอิงขอบเขตเดียวกัน
